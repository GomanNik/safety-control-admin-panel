# Первичное ревью проекта

Данный документ фиксирует первый обзор состояния репозитория после объединения frontend, backend и vision в одну ветку `main`.

## Общая оценка

Проект производит впечатление большого рабочего монорепозитория, в котором уже есть разделение на frontend, backend и vision runtime. Основная инженерная ценность сосредоточена в трех местах:

- развитый frontend-контур с сущностями, features, widgets и shared-слоем;
- backend-контур с Express-приложением, доменными модулями и shared HTTP/error foundation;
- vision-контур с подробной pipeline-логикой, тестами, runtime API и документацией по computer vision flow.

## Сильные стороны

1. Проект теперь находится в одной актуальной ветке `main`, что упрощает демонстрацию и сопровождение.
2. Структура frontend похожа на осознанное feature/entity/widget-разделение, а не на хаотичный набор компонентов.
3. Backend содержит shared-слой для ошибок, HTTP-ответов и валидации.
4. Vision runtime имеет явную pipeline-структуру: API layer, runtime orchestration, tracking, quality gate, observation, headwear detector, incident engine, storage.
5. В `vision/tests/` есть набор тестов по негативным сценариям, runtime, quality gate, crop geometry и track episode semantics.
6. `.gitignore` в целом правильно исключает тяжелые артефакты: модели, датасеты, видео, виртуальные окружения, сборки.
7. `.gitattributes` задает ожидаемые окончания строк для TS/JS/CSS/Python/Markdown и PowerShell.

## Главные проблемы

### 1. Документация не соответствует масштабу проекта

Корневой README слишком короткий для такого проекта. Он не объясняет:

- назначение системы;
- границы ответственности frontend/backend/vision;
- порядок запуска;
- порядок проверки;
- что хранится вне Git;
- какие документы читать дальше;
- что означает отказ от старого веточного разделения.

### 2. Старые документы частично устарели

`docs/REPOSITORY_GUIDE.md` ранее перечислял старые ветки `import/frontend`, `import/backend`, `import/vision-ml`, `integration/current-project`. После объединения это нужно заменить на модель одной основной ветки `main`.

### 3. Есть риск смешения production-кода и research/debug-инструментов

В `vision/` одновременно присутствуют:

- production runtime;
- dataset tools;
- debug scripts;
- review pack tools;
- test files;
- экспериментальные PowerShell-сценарии.

Это нормально для исследовательско-прикладного проекта, но требует явной документации: какие файлы являются production path, а какие являются вспомогательными.

### 4. Backend пока выглядит менее завершенным, чем frontend и vision

По структуре backend содержит много доменных модулей, но в app-level bootstrap явно подключен не весь список модулей. Это может быть нормальным промежуточным состоянием, но в документации нужно честно разделить:

- реализовано и подключено;
- заготовлено;
- планируется;
- требует интеграции.

### 5. Переменные окружения описаны недостаточно

Корневой `.env.example` содержит только frontend-переменные. Для полного запуска нужны отдельные примеры и пояснения:

- frontend `.env.example`;
- backend `.env.example`;
- vision `.env.example` или документированный блок runtime settings.

### 6. Lock-файлы требуют управленческого решения

В корне есть `pnpm-lock.yaml` и `package-lock.json`. Для frontend выбран `pnpm`, так как в package.json указан `packageManager: pnpm@...`. В таком случае наличие `package-lock.json` может путать. Его стоит оставить только если npm реально используется для корневого frontend-проекта. Иначе лучше удалить `package-lock.json` из корня после проверки.

Backend отдельно использует npm и имеет собственный `backend/package-lock.json`, это нормально.

## Рекомендации по улучшению

### Высокий приоритет

1. Обновить корневой README.
2. Обновить `docs/REPOSITORY_GUIDE.md` под одну ветку `main`.
3. Добавить README в `src/`, `backend/`, `vision/`, `scripts/`.
4. Разделить в документации production path и debug/dataset tools.
5. Добавить `.env.example` для backend и vision, если их еще нет.
6. Проверить, нужен ли корневой `package-lock.json`.

### Средний приоритет

1. Добавить `docs/API_CONTRACTS.md`.
2. Добавить `docs/DATA_MODEL.md`.
3. Добавить `docs/DEMO_SCENARIOS.md`.
4. Добавить `vision/docs/RUNTIME_ENDPOINTS.md`.
5. Добавить `vision/docs/DATASET_WORKFLOW.md`.

### Низкий приоритет

1. Добавить GitHub repository description и topics.
2. Добавить releases только после стабилизации демо-версии.
3. Добавить GitHub Actions для typecheck/build/tests.

## Предлагаемый порядок работ

1. Сначала привести документацию к фактической структуре проекта.
2. Затем выполнить технический аудит frontend.
3. Потом отдельно выполнить аудит backend.
4. Последним этапом выполнить глубокий аудит vision runtime, потому что это самая сложная часть проекта.

## Итог

Проект уже можно показывать как единый репозиторий, но документация пока не раскрывает масштаб и логику системы. Первая правильная задача — не глубокий рефакторинг кода, а создание понятной карты проекта и фиксация границ между production runtime, UI, backend API и исследовательскими инструментами.
